# Android 検証計画と未決事項

## 対象と導入方法

- 最低対応版は Android 8.0（API 26）を採用しました。これは開発上の選択であり、SKK がそれ以前で実装不能という意味ではありません。最低版を変更する場合は対応方針と検証対象を更新します。
- API 26 のエミュレーターと、基盤実装時点の安定版 Android のエミュレーターを境界試験に使います。compileSdk／targetSdk は 35、Build Tools は 35.0.0 に固定しました。境界 OS のエミュレーター試験は未実施で、現在の結合試験は API 30 です。
- 対象実機は Xiaomi Pad 8 と Pixel 7 です。両方ともユーザーが利用可能な最新 OS に更新済みです。Android の版・API レベル・ビルド番号は実機試験開始時に記録し、機種名から推測しません。キーボード型番・接続方法もその時点で記録します。
- ユーザーは英語配列を使用します。初期試験は英語配列で行い、US 固有のキー位置を前提にしません。JIS を含む複数レイアウトを対象とし、具体的なキーボードと OS の選択レイアウトは試験時に記録します。
- 最初の対象は検証用アプリの標準入力欄（複数行、検索、送信、パスワード、学習禁止、2 欄切替）です。ユーザーの優先対象は Chrome／Firefox、Gmail、Google Chat、Google Drive／Docs／スプレッドシート／Slides、Discord／Slack です。下表の順序は開発上の試験順序で、ユーザーが指定したアプリ間の順位ではありません。
- 開発者登録なしで ADB 導入から始めます。一般配布は日常利用版とは別に判断します。継続利用する APK の署名鍵を保管し、辞書のバックアップ後に更新を検証します。

## アプリごとの試験対象

| 試験順 | 対象 | 主な確認箇所 |
| --- | --- | --- |
| 1 | 検証用アプリ | 未確定表示・確定・削除・欄移動・送信の基準動作 |
| 2 | Chrome／Firefox | アドレス・検索欄、通常フォーム、複数行、リッチテキスト入力 |
| 3 | Gmail、Google Chat、Discord、Slack | 件名・本文・メッセージ欄、変換確定と送信の分離、改行、ショートカット |
| 4 | Google Drive | 検索、名前変更。文書編集先へ移動した場合は移動先アプリとして記録 |
| 4 | Google Docs、スプレッドシート、Slides | 本文・セル編集・テキスト枠・コメント、選択範囲変更、編集確定 |

ブラウザ版と Android アプリ版は異なる試験対象として記録します。ブラウザ以外はまず Android アプリ版を対象とし、Web 版も利用可能な範囲で Chrome／Firefox 上の追加試験に含めます。未検証の組み合わせを対応済みとは扱いません。両端末でアプリ版・OS 版・キーボード設定を残します。

## レイアウトの責務

Android が物理キーと修飾キーから文字へ対応付ける機構を持つため、IME はその結果を尊重します。`KeyEvent.getUnicodeChar` とイベントの修飾状態を使い、US 配列を仮定してキーコードから文字を自作しません。生のスキャンコードも端末共通の識別子として扱いません。

IME の責務は、その文字・修飾状態を SKK の入力やコマンドへ変換することです。文字入力と Ctrl 系コマンドの判定を分離し、Ctrl による制御文字化だけでコマンドを判定しません。初期のキー割り当ては論理文字を基準にし、物理位置を基準とする割り当ては必要に応じて別の設定として検討します。

記号、Shift／Caps Lock、AltGr、デッドキー、レイアウト切替を試験対象にします。AltGr の文字入力を一律にアプリのショートカットとして除外しないよう、[互換性仕様](compatibility.md)の Ctrl／Alt 引き渡し規則を適用する前に文字生成との関係を判定します。QWERTY 以外のレイアウトについても論理文字を正しく処理することを目指し、実機で確認したレイアウトだけを対応実績として公開します。

## 接続層の受入ケース

| ID | 操作 | 期待結果 |
| --- | --- | --- |
| I01 | Ctrl+j、Shift+文字、キーアップ、長押し | 定義した内部操作が順に届き、二重処理されません。修飾キー対応自体の可否は再調査しません |
| I02 | 候補表示中に Enter、その後もう一度 Enter | 最初は一度だけ確定し、検索・送信しません。次は入力先へ渡します |
| I03 | ASCII でアプリのショートカットを操作 | IME の割り当て以外は入力先の操作として機能します |
| I04 | 未確定文字表示を更新・削除 | 表示と内部状態が一致し、周辺の確定文字を巻き込みません |
| I05 | 辞書検索中に入力欄 A から B へ移動 | A の検索結果を B に反映しません。古い非同期結果を破棄します |
| I06 | 未確定中にアプリ側でカーソル・選択範囲を変更 | 古い位置を使った削除・確定を行いません。IME 自身の更新通知と外部移動を区別します |
| I07 | 再帰登録中に入力先切替・IME 切替 | 登録用文字を別の入力欄へ流しません。未保存の登録状態の終了方針を一貫させます |
| I08 | 回転、接続切断、プロセス終了 | 個人辞書を維持し、再開時に古い確定要求を再送しません |
| I09 | ソフトキーボードを出さず候補・注釈・登録を操作 | 状態を読め、物理キーだけで選択・登録・取消ができます |
| I10 | パスワード・学習禁止欄で入力 | パスワードを候補表示やログへ露出せず、学習禁止時は辞書を変更しません |
| I11 | 絵文字・結合文字の隣で削除 | UTF-16 の途中を破壊しません。登録内ではユーザーが認識する文字単位の削除を検証します |
| I12 | 辞書更新中断・ストレージ書き込み失敗 | 旧辞書を使え、成功と誤表示しません。保存失敗後の再試行で重複登録しません |
| I13 | 複数の OS レイアウトで英字・記号・修飾キー・デッドキーを入力 | OS の文字対応付けを保持し、SKK のキー割り当てが US 固有の位置に依存しません。未確定中のレイアウト変更でも以前のキー状態を持ち越しません |

## 性能の測定方法

デバッグログへ入力本文を記録せず、合成した入力と試験辞書を使います。リリース相当ビルドで機種、OS、辞書ハッシュ・件数、ビルド識別子を記録します。

| 指標 | 測定方法 | 判定時期 |
| --- | --- | --- |
| 初回表示 | プロセス停止状態と起動済み状態を分け、入力開始要求から状態表示までを各 30 回測ります | フェーズ 1 で予算を固定します |
| 打鍵反映 | 合成キーの受信から表示反映までを 1,000 回測り、p50／p95／最大値を記録します | フェーズ 1 で基盤予算、2 で変換込みを確認します |
| 辞書検索 | 小辞書・大辞書、初回・キャッシュ済み、送りあり／なし、補完を分けて各 1,000 回測ります | フェーズ 1 で暫定予算、3・4 で確認します |
| メモリ | 辞書導入前後、検索後、IME 非表示後の PSS を記録します | フェーズ 1 で予算、3・5 で確認します |
| 学習保存 | 合成の登録・順位変更と、保存中断後の再起動を検証します | フェーズ 3 |

性能目標値は測定前の推測で合格扱いにせず、フェーズ 1 の結果から明記します。エミュレーターの数値は実機の代用にしません。

## 第一のマイルストーンの判定

固定した DDSKK 参照、互換性一覧、必須機能の受入例、Android の試験計画を作成しました。対象端末などの未決事項は上表で管理します。実装・実機試験は次のフェーズです。実機対象・利用配列・優先アプリの選定も完了したため、フェーズ 0 の成果物は揃っています。正確な OS 版などの環境識別情報は次フェーズの実機試験開始時に記録します。
