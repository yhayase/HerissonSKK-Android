# 辞書性能測定

`DictionaryPerformanceAndroidTest` は、既存の `SQLiteDictionaryRepository` と
`DictionaryManager` を対象に、SQLite取り込み、管理情報の初期化、未キャッシュ検索、キャッシュヒット、個人学習を測定します。

## 2026-09-19 の測定境界変更

通常経路はSQLite正本とする有限キャッシュへ変更済みです。新しい測定は初期化を `metadata_ready_ms`、学習保存後の反映を `personal_learning_publish_ms` として記録します。旧 `load_publish_ms`・`personal_learning_reload_publish_ms` は後半の過去測定だけに残します。

初期化は取り込み用の接続を閉じた後、別のSQLite接続を開いて管理情報を準備するまでです。候補全件の読み込み、見出し検索、補完検索の各カウンターが初期化時に0であることを検証します。OSのページキャッシュは取り込みで温まっています。初回検索はアプリの辞書キャッシュが空の状態から、この試験用スレッドで未取得レコードの読み込みを完了させた時間、反復検索はStrictModeでディスクI/Oを禁止したキャッシュヒットです。IMEの入力スレッドが同じ待機を行うわけではありません。

キャッシュ上限を超える異なる未登録見出しを検索し、件数・候補レコード数・保持文字数の上限と、追い出し後に保存先から再取得できることを確認します。個人学習の保存後に全件・検索・補完の読み込みカウンターが増えないことも検証します。性能の大小だけでなく、処理量の契約を合格条件にします。

PSSには試験が生成した辞書フィクスチャなども含まれます。キャッシュの保持量と区別し、PSS全体やその差を辞書キャッシュだけのメモリー使用量と解釈しません。

## 最終APKの比較結果（2026-09-19）

API 26の同じ `emulator-5582`、同じseed・合成10万見出し・64回の反復で比較しました。旧版は配布済み `1b9faa2`、新版は未コミット変更のない `a1d748a` のAPKです。実機の入力開始までの総時間ではなく、辞書の対象処理の時間です。

| 測定対象 | 旧版 | 新版 |
| --- | ---: | ---: |
| 辞書準備（旧全件読込／新管理情報準備） | 778.993 ms | 1.379 ms |
| 個人学習の保存から反映まで | 775.680 ms | 2.620 ms |
| 通常検索のキャッシュヒット p95 | 0.053 ms | 0.044 ms |

新版の未キャッシュ通常検索は0.687 ms、未キャッシュ補完は2.492 msでした。初期化時の候補・補完・全件読み込み回数はすべて0でした。キャッシュ上限を超える未登録語を検索した後も128件以内で、追い出された正当な候補はSQLiteから再取得できました。学習後の全件読み込みもありません。

旧版レポートは `app/build/reports/dictionary-performance/emulator-5582/20260919T000915Z`、新版は `20260919T001705Z` です。旧版は変更中ソースをビルドせず、保存済みAPKのハッシュを照合して測定したため、その旨をメタデータに追記しています。両測定の記録を `build/distributions/a1d748a/performance-baseline` と `performance-final` にも保存しました。新版の1,000見出しと100,000見出しの双方で性能試験の機能・処理量検査が成功しています。

## 対象

フィクスチャは固定 seed `20260916` から instrumentation 試験内で生成します。生成見出しは重複しない
ひらがなの読みであり、数字正規化で意図せず同一視されません。複数候補と注釈、送りあり、数値テンプレート
（`だい#`）、補完、個人学習後の保存・反映を含みます。これはアプリ固有の合成入力であり、実 SKK
辞書の分布を代表するものではありません。

各結果には件数、エンコード後のバイト数、SHA-256、seed、取り込み・読み込み・個人学習公開時間を記録します。
通常、送りあり、数値、補完の各公開済み検索経路について、初回時間とキャッシュ済み検索の p50/p95/max も
記録します。PSS は読み込み前・後・close 後に記録します。共用エミュレーターの時間は変動するため、時間の
合格閾値は設けません。代わりに検索結果と、StrictMode で確認できる範囲のキャッシュヒット時のディスク I/O 不在を検証します。

## 実行

先に debug APK をビルドし、専用エミュレーターだけで実行します。runner は `adb install -r` を使い、IME を
選択せず、パッケージの clear もしません。試験は UUID 付き一時 DB を作成し `finally` で削除するため、
利用者の辞書 DB や設定は変更しません。

```sh
./gradlew :app:assembleDebug :app:assembleDebugAndroidTest
python3 scripts/measure-dictionary-emulator.py --serial emulator-5554
python3 scripts/measure-dictionary-emulator.py --serial emulator-5554 --smoke
```

`--entries 1000,100000` と `--samples 256` で既定値を変更できます。件数は 4〜100,000、件数の指定数は
最大 4、反復数は 1〜2,048 に制限します。空の指定や重複した件数は拒否します。`--smoke` は 1,000 件・
16 回で接続確認を行います。レポートには API、commit、dirty 状態、APK hash、instrumentation 出力、
抽出済み測定行を `app/build/reports/dictionary-performance/` 以下へ保存します。

## 解釈

これは選択したエミュレーター上の debug Android instrumentation 測定です。100k の有限キャッシュを使う検索が
その環境で十分軽そうかを判断する材料にはなりますが、release build、実機、電池、起動、利用者端末の受入結果
ではありません。同じ emulator image で反復し、結論を出す前に記録済み metadata を確認します。


## 2026-09-16 の初回測定

API 30 の `emulator-5580/20260916T060336Z` で 1,000 件と 100,000 件を各 256 回測定し、検索結果と StrictMode 検査を含む 1 試験が成功しました。ソースは `507878b` に未コミットの設定機能と測定コードを加えた状態で、APK hash は履歴に保存しています。

100,000 件では取り込み 1,758.867 ms、読み込み・公開 824.005 ms、個人学習後の全件再公開 839.100 ms でした。公開済み検索の p95 は通常 0.021 ms、送りあり 0.016 ms、数値 0.042 ms、補完 0.085 ms です。初回検索はプロセス全体の cold start ではなく、各フィクスチャ公開後の初回です。

当時はこの結果から、検索そのものより学習ごとの全件再構築を性能検討対象としました。現在は上記の有限キャッシュ方式へ移行済みです。処理はバックグラウンドですが、公開完了までの時間と連続学習の待機量は引き続き測ります。PSS は生成済みフィクスチャや前の試験、GC の影響を含むため、前後の差だけを辞書の所要メモリーと解釈しません。実機受入の閾値達成は未確認です。


同日 `emulator-5580/20260916T061901Z` で最小件数 4 件も含めて再検証し、全結果が成功しました。100,000 件の再公開は 842.667 ms であり、初回と同じ傾向でした。最小件数では存在する補完候補数に合わせて検証し、選択する probe も生成済み見出しの範囲内に制限します。
