# フェーズ 1 の実装・検証記録

本書は旧フェーズ1当時の履歴です。「未実装」等は当時の状態であり、現在の残件には使いません。現在の計画は [ロードマップ](roadmap.md)、実装証拠は [試験対応表](test-coverage.md) を参照します。

## 実装したもの

- Kotlin の Android アプリと Gradle Wrapper を作成しました。最低対応版は API 26 とし、compileSdk／targetSdk は 35、JVM ターゲットは 17 に固定しました。
- `SkkInputMethodService` は入力方法として登録され、物理キーを受け取り、文字キーの画面を作らずに入力モード・候補を表示します。Android 9 以降では候補のウィンドウ表示も明示的に要求します。
- `HardwareKeyMapper` は OS が生成する文字と修飾状態を処理します。Ctrl+j／Ctrl+g、Enter、Escape、Backspace、AltGr とデッドキーを扱い、未処理の操作は入力先へ渡します。
- `KeyPressLedger` はキーの押下からキーアップまで処理結果を保持します。変換を確定した Enter の長押しが、続けて送信キーにならないようにしています。
- `EditorSession` は入力接続をセッションごとに保持します。自分が行った未確定表示の更新と、入力先で行われた選択範囲変更を区別します。入力先を変更した後に古いセッションから文字を出力しません。
- パスワードと `TYPE_NULL` の欄は直接入力として扱い、候補表示を出しません。学習禁止フラグをセッションへ引き継ぎます。学習・辞書保存自体は未実装です。
- 導入・状態表示の設定画面と、独立した入力確認アプリ（`test-editor`）を用意しました。検索・送信操作はカウントするだけで、外部へは送信しません。アプリはネットワーク権限を持ちません。

## 検証用エンジンの範囲

`PilotEngine` は Android 接続を確認するための限定実装です。独自に作成した母音・カ行・ナ行・ハ行・`nn` の規則と、`にほん` → `日本`／`二本` の固定候補を持ちます。大文字で見出し語入力に入り、Space で候補表示、Enter で確定、Ctrl+g で取消できます。`l` で直接入力、Ctrl+j でかなへ戻ります。

これは DDSKK 互換の完成したコアではありません。候補を使い切った際は巡回し、未知の読みはそのまま候補にする、接続検証用の挙動です。送り仮名、単語登録、全候補操作、補完、完全なローマ字規則は未実装です。フェーズ 2 で受入仕様に沿うコアへ置き換えます。ブラウザ版や DDSKK の実装ソース・辞書は複製していません。

## 入力先移動時の方針（D03）

カーソル・選択範囲の外部変更、入力接続の終了、端末構成やキーボードの変更を検出したときは、既に入力先へ表示した文字をその位置に残し、`finishComposingText` で未確定状態を終了します。新しい位置へ文字を再挿入したり、以前の位置を推測して削除したりしません。IME 内部の読み・候補・未消化アクセントは引き継ぎません。

これは変換候補を確定したことによる学習とは分離します。登録画面の文字は未実装のため、登録中断の具体的な UI はフェーズ 3 で追加します。接続先が API の失敗を返した場合は、そのセッションで変換を停止し、同じキーを二重配送せず、接続の再確認を表示します。

将来の非同期辞書検索はまだ組み込んでいません。現時点の世代チェックは古い入力セッションを拒否する基盤であり、同一セッション内の検索要求の識別・取消は辞書処理の導入時に追加します。

## 検証環境と結果

- ローカルテストは JUnit／Robolectric を使い、Android API 26 と 35 のモデルで実行します。純粋なキー押下管理は JVM 単体で検証します。
- 結合試験は専用の Android 11（API 30）x86_64 エミュレーターで実行します。Android の入力配送を通して物理キー相当のイベントを注入します。実際の USB／Bluetooth キーボードの検証とは区別します。
- 主なケースは Enter の確定・送信分離、キーアップとリピート、選択範囲変更、入力先変更、接続エラー、初期選択位置が不明な入力先、パスワード判定、論理文字に基づくキー割り当て、AltGr、デッドキーです。
- Gradle Wrapper による APK ビルドが成功しました。ローカルテスト 47 件、別アプリとの結合試験 3 件が成功しました。結合試験は IME プロセス停止後の起動も含みます。両アプリの Lint はエラー 0 件です。テスト依存の新バージョン通知などの警告は残っています。
- 結果は `app/build/test-results/testDebugUnitTest/`、`test-editor/build/reports/emulator-instrumentation.txt`、各モジュールの `build/reports/lint-results-debug.html` に生成します。ビルド結果は Git 管理外です。

## 実機での確認（2026-09-12）

Xiaomi Pad 8 へ MTP でデバッグ APK を転送し、ユーザーがファイルからインストールして IME を有効にしました。「USB 経由でインストール」では Mi Account のログインを求められましたが、ファイルからのインストールは成功しました。

ユーザーから、案内した確認を一通り実施し、今のところ問題はないとの報告がありました。案内した範囲は、かな入力、`Nihon` の変換・候補切替・前候補・Enter 確定と次の Enter の通常動作、Ctrl+g による候補／読みの取消、英字／かな切替、カーソル移動、入力欄・アプリ切替、候補表示とソフトウェアキーボードの表示状態です。これはユーザーによる手動確認の報告であり、個別ケースの計測ログはありません。

追加報告で、次の環境と結果を確認しました。

- 端末は Xiaomi Pad 8、Android 16、HyperOS 3.0.303.0 です。
- キーボードは任天堂の DS ポケモンタイピング付属 Bluetooth キーボードです。物理配列は日本語配列で、OS の認識は当初日本語配列でしたが、その後、英語配列への切り替えができたとの報告がありました。
- Chrome／Firefox のアドレス欄で、案内した `Ctrl+j` → `Nihon` → `Space` の後、最初の Enter は確定のみ、次の Enter で検索されることをユーザーが確認しました。ブラウザーの版と、この確認時の選択レイアウトは未記録です。

Chrome のアドレス欄では、候補表示後に Enter を約 2 秒長押ししても確定のみで検索されず、離してもう一度短く押すと検索されることもユーザーが確認しました。「SKK 入力確認」アプリでの確認としては扱いません。

Chrome のアドレス欄で `Ctrl+j` → `l` による英字入力へ切り替え、英語配列の Shift+2／6／7／8／9／0 がそれぞれ `@^&*()` になることをユーザーが確認しました。その他の記号・修飾キーや日本語レイアウトでの動作は未確認です。

Chrome のアドレス欄で英字入力中に `abc` → `Ctrl+a` → `z` と操作し、全選択した文字列が `z` のみに置き換わることをユーザーが確認しました。英字入力時にアプリの全選択ショートカットが機能しています。

上記はユーザーによる手動確認の報告です。チャットなどの送信操作や、ブラウザー内の他の入力欄の検証とは区別します。

追加の手動確認では、次の報告がありました。

- 別の入力欄をタップすると元の欄で候補が確定されました。この動作は許容します。
- 画面回転で候補が確定されたような状態になり、未確定表示のアンダーラインが残りました。
- Bluetooth キーボードの電源断でも候補が確定されたような状態になりました。追加確認で、再接続後に入力を再開できるとの報告がありました。切断前の候補を保持して変換を継続する動作とは区別します。

回転・電源断時は候補を保持する動作が望ましいものの、ユーザーの判断で当面は現状を許容します。アンダーラインの不一致を含め、[ロードマップの将来の改善項目](roadmap.md#将来の改善項目)として記録しました。今回、実装の変更は行っていません。

## ADB 接続と性能測定の予備確認（2026-09-12）

ADB で Xiaomi Pad 8 が認証済みの `device` として接続されていることを確認しました。端末から取得した値は Android 16、API 36、ビルド番号 `BP2A.250605.031.A3` です。インストール済みの SKK は `versionName=0.1.0-dev`、`versionCode=1` のデバッグビルドです。ソースコミットとの一致は未確認です。

現在のプロセスに対する `dumpsys meminfo jp.hayase.skk` の単発取得では、TOTAL PSS は 58,911 KB、TOTAL RSS は 127,262 KB、TOTAL SWAP PSS は 38,741 KB でした。入力・表示状態や起動後の経過時間を統制していない予備値で、性能目標の判定には使用しません。リリース相当ビルドでの初回表示・打鍵反映・状態別メモリの測定は未実施です。

測定用の別パッケージ APK と自動測定スクリプトを準備しました。手動導入後の照合と測定テスト APK の更新が完了しました。測定処理全体は API 30 エミュレーターで成功しましたが、Xiaomi Pad 8 では入力確認アプリのウィンドウを観測できず、表示待ちで停止しています。測定終了後の ATOK への復帰は確認済みです。測定境界と検証状況は [実機の性能測定](performance.md) を参照してください。

## 実機で残る確認

Xiaomi Pad 8 の初回手動確認は上記のとおりです。今後の実機確認も Xiaomi Pad 8 で継続し、Pixel 7 の確認はフェーズ完了条件に含めません。ブラウザーの版などの環境情報の補完、優先アプリの残る入力欄の確認、配列ごとの記号・修飾キーの確認が残っています。API 26／35 のモデルテストは、その OS のエミュレーター試験を代替しません。

性能目標はまだ固定していません。初回表示、打鍵反映、メモリは実機で測定して予算を決めます。固定候補しかない段階では大辞書の検索時間を評価できないため、辞書検索はフェーズ 2・3 の測定へつなげます。

フェーズ 1 は基盤実装とローカル検証を進めた状態です。ロードマップに定めた実機確認と性能目標の固定が残るため、フェーズ全体を完了とは扱いません。
