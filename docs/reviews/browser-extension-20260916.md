# ブラウザ版の実装・テストを Android 版へ活用する評価

履歴資料です。対象時点の判定を保持しています。現在の仕様・残件との区別は [レビュー履歴の案内](README.md) を参照します。

評価日: 2026-09-16

## 結論

ブラウザ版は、基本変換と辞書管理の設計・テストを出発点にする価値が高いです。AndroidSKK の基盤からテスト可能な境界を作り直すより、既存の操作例と辞書の契約を利用し、Android 用のコアと接続層を整える方針を推奨します。ただし、これは見積もりを伴う工数比較の結果ではなく、確認した再利用資産と不足に基づく判断です。

特に参考になるのは、入力と期待結果を持つテスト、辞書と保存先の差し替え、再帰登録の状態遷移、辞書更新失敗時の旧版保持です。TypeScript の機械的な Kotlin 変換だけでは、内部カーソル編集や Android 固有の確定・接続・プライバシー要件は満たせません。

前回の「コアが編集先から分離されている」という説明には補足が必要です。具体的な DOM への依存はインターフェースで切れていますが、コアは依然として編集先に未確定文字やマーカーを挿入し、そこから読みを取得します。Android ではコア自身が未確定状態を所有する設計へ変更します。

## そのまま移すと問題になる箇所

### 1. 編集先の抽象化と、状態の所有は別です

`src/core/skk/editor/IEditor.ts` はテキスト編集、読みの抽出、候補表示、登録画面、モード変更をまとめています。`MidashigoMode`／`AbbrevMode` は `▽` を挿入し、`extractMidashigo()` で編集先から読みを取り出します。`AbstractKanaMode.insertStringAndShowRemaining` も編集先への挿入と表示を実行します。

Android 版では、読みや `▽` の位置を入力先から復元する必要がないようにします。コアが入力状態を保持し、確定文字・未確定表示・候補の更新を出力します。マーカーの表示と内部状態を分けます。辞書インターフェースの分離は踏襲しますが、広い `IEditor` をそのまま InputConnection のラッパーへ移すことは推奨しません。

### 2. Enter／C-j と送り条件には、確認済みの差があります

| 限定プローブ | ブラウザ側で確認した結果 | Android の採用仕様 |
| --- | --- | --- |
| ひらがな状態で `n Enter` | `ん` と改行 | `ん` の確定のみ |
| ひらがな状態で `n C-j` | 残余が消え、文字は出ません | `ん` を確定します |
| `おおk /大/多/[く/多/]/[き/大/]/` を `Entry.forOkuri('く')` で絞る | 候補順は `大`、`多` | 個人辞書の一致優先で `多く`、次が `大く` |

Enter/C-j は既存の `MockEditor` でコアを実行した結果です。Android アプリや実ブラウザ画面での再現報告ではありません。送り順はパーサー＋Entry の局所検証で、個人辞書の取り込み経路全体を実行したものではありません。それでもこれらをそのまま Android の期待値にできないことは確認できます。

根拠は `henkan/KakuteiMode.ts` の `onEnter`／`onCtrlJ`、`jisyo/entry.ts` の `forOkuri` です。`MidashigoMode.onEnter` と `AbbrevMode.onEnter` にも改行挿入があります。`content.ts` が Enter イベントを抑止していても、コア内の改行挿入がなくなるわけではありません。

### 3. 登録ミニバッファは、途中編集・Unicode の完成実装ではありません

`RegistrationMiniBufferEditor` を、外部の `ITextTarget` を付けない内部バッファとして実行しました。

- `😀` を挿入して `deleteLeft()` を呼ぶと、UTF-16 の上位サロゲート `0xd83d` が残ります。実装は `slice(0, -1)` です。
- `東京` の先頭1文字を `replaceRange` で `京` に置き換える操作は、`京京` ではなく `東京京` になります。範囲を使わず末尾に追加しています。

これは内部バッファの API を直接呼んだ確認です。全ブラウザ UI の操作経路で同じ問題が出ると断定するものではありません。Android 版の F05／F06／N08 を満たす部品として、無変更で採用できない根拠です。

### 4. テスト用の編集実装にも意味のある処理があります

`test/unit/mocks/MockEditor.ts` は、文字列・カーソル・マーカー・候補の確定や文字種変換を実装しています。モードのテストはこの編集実装との組み合わせの合格であり、コアだけで全状態を所有できる証明ではありません。登録の47件も実際には BrowserEditorAdapter／HUD と DOM の代替実装を使います。

Android では、キー列を渡して「内部状態・確定出力・辞書要求」を観測できるテストへ移します。モック側へ変換ロジックを再実装しすぎないようにします。

### 5. 共通化の境界と設定を作り直す部分があります

- `EditorFactory` は共有の静的状態を持ち、テストで差し替えています。コンストラクターで `IEditor` を渡す経路もあるため、全面的に依存注入できないわけではありません。Android では入力セッションごとの明示的な依存を使います。
- `RomajiInput` は `romKanaBaseRule` を直接参照します。規則データは参考になりますが、設定したテーブルをセッションへ渡す契約が必要です。
- `MenuHenkanMode` は `asdfjkl` と7件を固定しています。Android の可変候補数・選択キー変更は追加設計です。
- `Entry.onCandidateSelected` はエラーに見出し語を含めてログ出力します。Android の入力本文をログに残さない方針に合わせます。
- 32個の core TypeScript ファイルに完成した機能が集約されているとは扱いません。辞書管理・設定・接続は core の外にもあり、再利用範囲はモジュール単位で判断します。

## 取り込み方針

1. ブラウザ版のローマ字・基本変換・送り・取消・再帰登録のテストから、初期モード、辞書、キー列、期待する未確定状態、確定出力、保存結果を抽出します。Android 要件 ID を付け、DDSKK 17.2 の採用プロファイルとの差を記録します。
2. Kotlin のコアは内部バッファとカーソルを所有し、実辞書・Android UI なしで試験できるようにします。状態の分類と辞書の契約はブラウザ版を参考にします。
3. 辞書のパーサー・候補モデル・世代更新のテスト条件を移し、保存処理は Android で中断・再起動を検証します。JSON 辞書の採否やブラウザの制限値を自動的に製品要件へ追加しません。
4. Enter、Q、送り優先、Unicode、編集失敗、学習禁止、入力先変更を Android 固有の回帰ケースとして追加します。既存ブラウザのテスト合格で代替しません。
5. ローマ字規則・ソースを実際に複製する前に、元の出典とライセンスを確認します。今回参照リポジトリの追跡対象に LICENSE／COPYING は確認できませんでした。利用不可と断定するものではなく、取り込み前の確認事項です。

基本コアと辞書管理については、仕様・テストをゼロから作る必要がありません。一方、内部編集、設定の一般化、高度変換、Android 接続は残る開発範囲です。既存487件のうち何％をそのまま移せるかという数値は、期待値の個別照合と Kotlin 側のテスト境界が決まる前には算定しません。

## 再実行と成果物

既存テストのスナップショットでは、元の `vitest.config.ts` を読み込み `cacheDir` のみ `/tmp` に向ける調査用設定を使用しました。Vite の設定バンドルは読み取り専用 node_modules への一時書き込みを試みたため、`--configLoader runner` を指定しました。また、参照元に生成済みの `.wxt/` をコピーしました。これらは環境準備上の問題で、テスト失敗としては数えていません。

```sh
# 上記スナップショットのルートで実行します。
node node_modules/vitest/vitest.mjs run --config assessment.vitest.config.ts \
  --configLoader runner --reporter=json --outputFile=test-results.json
```

追加プローブは [browser-core-probes.test.ts](../../scripts/review/browser-core-probes.test.ts) に保存しました。スナップショットの `test/unit/android-assessment.test.ts` へコピーし、そのファイルだけを Vitest で指定します。ブラウザ版の製品テストへ追加・修正はしていません。上の全件実行結果487件は追加プローブを置く前の結果で、プローブ5件は別実行です。

[結果 JSON](browser-extension-20260916-results.json) に、ファイル別成功件数、診断結果、参照元ハッシュを保存しています。数値は今回のローカル環境での結果です。評価後の文書・診断用ファイルはチェックポイント後の変更として残し、実装の移植はまだ開始していません。
