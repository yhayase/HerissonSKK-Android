# API 36 公開要件への対応（2026-09-23）

## 目的と変更

Google Play の新規提出要件に合わせて、アプリと試験用エディターの compileSdk／targetSdk を35から36へ更新します。minSdk は26のままです。API 36 を正式サポートする Android Gradle Plugin 8.10.1 を採用し、Gradle 8.11.1 と Kotlin 2.1.20 は維持します。

根拠は [Google Play 対象 API 要件](https://developer.android.com/google/play/requirements/target-sdk?hl=en)、[AGP 8.10 の互換性](https://developer.android.com/build/releases/agp-8-10-0-release-notes)、[Android 16 の対象 API による変更](https://developer.android.com/about/versions/16/behavior-changes-16)です。

設定画面は既に AndroidX の戻るコールバックとシステムバー・IME の inset 処理を使っています。試験用 WebView エディターにも他の試験用画面と同じ inset 処理を適用します。API 36 専用エミュレーターを追加し、所有者の実機は変更しません。

ローカル検証へ release AAB のビルドと同梱通知7件の本文照合、APK の minSdk 26／targetSdk 36 照合を追加しました。署名鍵生成、Console 登録・アップロード、公開は含みません。

## 検証中に見つかった問題

- 物理候補表示中の Back で入力先 Activity が閉じる問題を API 36 で再現しました。Android 16 は Back の押下を IME に転送し、キーを離すときにその時点の最優先コールバックを呼びます。従来処理は押下時にホストを閉じ、追加したコールバックも解除していたため、キーを離すと入力先の終了処理へ切り替わっていました。押下ではキー追跡だけを開始し、通常のキー解放または予測型 Back のコールバックで閉じるよう修正しました。取消されたキー解放では閉じません。API 33 以降のコールバックはホスト表示中だけ登録し、入力終了・非表示・構成変更・サービス終了で解除します。
- IME 選択画面の試験は、旧 OS の ListView と checkable な項目を前提にしていました。API 36 では RecyclerView と selected な行になっています。実画像とアクセシビリティ階層で画面自体の正常表示を確認し、システム画面内の選択中の IME を実際にタップし、閉じることと既定 IME が変わらないことを検証するよう改めました。

## 証拠の扱い

作業中の記録は `build/reports/local-verification/` と `test-editor/build/reports/customization-e2e/emulator-5588/` に保存します。診断用 APK と最終成果物は区別します。途中でビルドし直した試験のメタデータを最終成果物の証拠として流用しません。最終結果は診断除去後の同じ成果物に対する検証で確定します。

## 独立検証

通常の調査・実装後、別担当が SDK 36 の `ViewRootImpl`、`InputMethodService` とコールバック転送を確認しました。最初の登録処理と遅延登録だけでは E2E が失敗し、難度を complex から demanding へ上げて調査しました。ウィンドウ接続不足と単純な再登録不足の仮説は実行結果から採用しませんでした。Back 直前の入力先ウィンドウには優先度1000000の IME コールバックが存在し、押下後に解除されること、SDK が解放時に最優先処理を取り直すことが原因特定の根拠です。最終の押下／解放修正と取消・ライフサイクルは別担当も妥当と判定しました。

新しい単体試験の試験用キーボード生成で API 26 に存在しない Builder を参照していた問題は、既存の Robolectric ShadowInputDevice を継承する試験用 shadow に直しました。製品側の API 26 互換性の不具合とは区別します。

## 入力開始待ちの修正と追加検証

API 26 の `lあc` は、Android の `InputMethodManager.isActive` だけを待ち、SKK の入力セッション開始を待っていなかった試験で発生しました。サービスは設定読込中にはキーを入力先へ渡すため、この待機条件では直接入力の切替キーを早く送る可能性があります。ただし、その失敗時点のライフサイクル記録がないため、個別事象の競合経路までは断定しません。

文字を消して期待値になるまで再入力する案は、実際のキー処理の欠陥を隠すため採用しませんでした。独立検証では、座標監視要求も当初はセッション作成前に発生し得ると分かりました。サービスを有効なセッションの作成後だけ監視を開始する順序へ修正し、試験用エディターで現在の接続に対する監視要求を確認してから入力を始めます。接続の世代を照合し、閉じた接続の応答は新しい入力欄の準備完了に使いません。既存の正確な本文・選択位置・Enter 通知の検査を維持します。文字送出もイベント時刻を更新する `sendStringSync` に統一しました。

この待機は、新しい Activity と入力接続を作る現行試験の初期準備を対象とし、同一接続の再起動全般の準備完了判定ではありません。独立担当がサービスと試験側の条件を照合しました。追加した回帰試験は実際の `onWindowShown()` 経路で開始前の要求ゼロと開始後の監視開始を検査し、ガードを一時除去すると API 26 で意図した assertion が失敗することも確認しました。ガードは復元済みです。

API 36 の幅800dp相当（密度240、1600×1200／1200×1600）の設定画面は、縦横各4件が成功しました。ヘッダー・保存操作の固定、長いページのスクロール、設定の表示列、未保存変更の戻る操作を検査しました。縦画面の画像も目視確認し、端末の画面サイズと密度の復元を照合しました。記録は `build/reports/api36-release-matrix-20260923/wide-result.json` です。
