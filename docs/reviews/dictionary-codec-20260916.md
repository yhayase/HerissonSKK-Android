## 実装契約

UTF-8／EUC-JP を strict に復号し、SKK テキストを不変の見出し語・候補モデルへ変換します。候補本文、注釈、送り条件を分離し、ファイル順を保って重複を統合します。書き出しは UTF-8、LF、BOM なし、末尾改行ありです。

DDSKK の `(concat "...")` は単一文字列と `\057`、`\073`、`\\`、`\"` だけを専用 parser で処理します。Lisp evaluator への経路はありません。任意の式、不正行、不正 Unicode は行番号と理由分類だけを含む例外で取り込み全体を拒否し、辞書本文をエラーへ含めません。

## 実装中レビューの指摘と解決

| 指摘 | 解決 |
| --- | --- |
| リテラルの注釈が `*` で始まると、書き出し後の再解析で DDSKK の個人注釈マーカーとして除去されました | `*` で始まる注釈を限定 `concat` で符号化し、リテラルの星を保持する往復試験を追加しました |
| 候補本文が `(concat` で始まり閉じ括弧がない場合、書き出しは生文字列、再解析は不正な式として拒否しました | `(concat` で始まるリテラルを閉じ括弧の有無によらず限定 `concat` で符号化し、往復試験へ追加しました |
| 同一見出し語の重複統合が候補ごとの線形探索で、悪意ある大量候補に対して二乗時間になりました | 見出し語ごとの `LinkedHashMap<(本文, 送り条件), 候補>` に変更し、順序と注釈規則を保った線形統合にしました。50,000 候補の時間上限付き回帰試験を追加しました |
| `parseText` がバイト入力の上限を迂回し、改行分割が全行のリストを先に確保していました | 復号済み文字列を 67,108,864 UTF-16 code unit 以下に制限し、行を逐次走査する実装に変更しました |

送り条件の境界確認では、先頭の促音を除いた最初のかなから子音を求めるよう修正し、`っか` と `k` の受入試験を追加しました。失敗メッセージは日本語にし、機械判定用のエラー種別は別に保持します。

最終整合確認では、直接文字列を受け取る `parseText` がコメントと空行を除外してから Unicode を検証していたため、無視するコメント内の孤立サロゲートを受理できることを確認しました。解析前に全文の UTF-16 を走査し、CR、LF、TAB 以外の C0 制御文字、DEL、孤立サロゲートを本文を含めない行番号付きエラーで拒否するよう修正しました。コメント内の孤立サロゲートを使う回帰試験を追加しました。

## 独立レビュー

別担当が codec、モデル、試験、複合辞書との境界を読み取り専用で確認しました。安全な限定文法、候補順、送り条件、重複規則、公開 API について具体的な追加指摘はありませんでした。

## 検証結果

- codec 限定試験: 18 件成功
- `:core:test`: codec 18 件、複合辞書 8 件、既存 63 件の合計 89 件成功
- Android 側試験: 別の全体検証で 67 件成功

独自の最小 fixture だけを使用し、DDSKK、AquaSKK、ブラウザー版のソースや辞書 fixture は複製していません。

## 残る制約

- 64 MiB の入力ファイル上限と 67,108,864 UTF-16 code unit の復号後上限は防御的な初期値です。Android 実機のヒープ上限に対する最大辞書の取り込み測定は未実施です。
- codec は Android のファイル選択、辞書管理、永続化へまだ接続していません。K13 の端末上の取り込み・書き出し完了を示すものではありません。
- システム候補の抑止記録、由来、内部操作 ID を含む完全バックアップ形式は未確定です。標準 SKK テキストの往復対象には含めません。

追加した全文Unicode検証と、基本変換の生成キー列試験を含む主担当の最終 `:core:test` は91件成功、失敗・エラー・スキップ0件でした。形式層19件、複合検索8件、既存63件、32 seedで計16,000操作を確認する不変条件試験1件の内訳です。
