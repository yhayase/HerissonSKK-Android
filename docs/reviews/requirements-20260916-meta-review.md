### 指摘 1: 内部 Q と見出し語 q

DDSKK の `skk-vars.el:947–949` と `skk.el:3298–3318` を確認しました。Q は現在位置で新しい見出し語を開始でき、既存文字の取り込みを必要としません。`skk.el:935–972` は見出し語の文字種変更後に確定します。独立プローブでも `Q kana C-j` は `かな`、`Kana q` は `カナ` でした。

一方、修正前のロードマップ「仕様の境界」は、内部 Q の操作を別途定義すると既に記載しています。したがって、仕様が Q 全般を誤って対象外にしたとは判定できません。不足は基本操作の受入例と、明示された保留事項の期限・状態表への接続です。F02 の文字種変更を具体化する q の例と、既存バッファを取り込まない基本 Q の例は妥当です。候補中・未消化ローマ字中・途中カーソルでの全挙動は、U01 などへ接続して実装前に確定できます。今回のレビューだけで、その全仕様を採用済みにする必要はありません。

### 指摘 2: Enter の参照説明と残余文字

`skk.el:5222–5223` の改行抑止条件は `skk-egg-like-newline` と `skk-henkan-mode` です。独立実行で設定を t にしても `n RET` は `ん\n`、`k RET` は `\n` となり、一次レビューの結果を再現しました。製品が未消化ローマ字だけでも改行・送信を抑止する仕様は明示されており、誤りではありません。同等性の説明だけを限定する必要があります。

標準設定の `k Enter` を残すか捨てるかは、「規則上の確定結果または残余文字」だけでは確定しません。明確化は妥当ですが、DDSKK の再現結果だけから Android 側も捨てると決めてはいけません。既存の製品方針に沿って標準ケースを固定し、カスタム規則の一般的な終端規則は U03 と結び付けられます。送信抑止と、残余文字の出力内容は別の判断です。

### 指摘 3: 送り条件の比較設定

`skk-vars.el:1584–1645` で、厳密一致による除外と、一致候補の優先が異なる設定であり、両方の既定値が nil であることを確認しました。K04 の一致優先は既に明確な採用仕様です。また、互換性文書は Android 向けの選択を優先するため、DDSKK の標準値との差だけで製品仕様の矛盾にはなりません。

不足しているのは再現可能な比較条件です。比較時の `skk-henkan-strict-okuri-precedence = t` と、`skk-henkan-okuri-strictly = nil`、`skk-process-okuri-early = nil` を明示し、一致・不一致候補のある個人辞書で期待順を固定する修正は妥当です。既存の試験辞書説明にも送り条件の別ケースを作る予定はあるため、「送り条件の試験計画が全くない」とは扱いません。複数辞書全体での順位や厳密除外の採否は U06／R01 の未決範囲を維持します。

### 指摘 4: 特殊な入力欄

F10／N05／K19 は学習・登録保存の抑止を、I10 はパスワードの候補表示・ログへの露出禁止を既に要求しています。通常の開始モード試験だけで十分とは書かれておらず、保護要件そのものの脱落ではありません。未定義なのは、この制限と C-j など通常キー表の具体的な優先関係です。

`SkkInputMethodService.kt:44` はパスワードまたは TYPE_NULL を保護対象とし、`input/EditorSession.kt:28` は保護対象のキーをコア処理せず返します。これは `phase1.md` の直接入力・候補非表示の記録とも一致します。この現行方針を製品上の例外として明文化し、C-j 後も変換・登録に入らない受入例へ接続する修正は妥当です。現在の漏えい、不具合、または新規のセキュリティ対策が必要だとする根拠はありません。学習禁止フラグだけの通常入力欄まで変換を禁止しないようにします。[学習禁止フラグの公式仕様](https://developer.android.com/reference/android/view/inputmethod/EditorInfo#IME_FLAG_NO_PERSONALIZED_LEARNING)

TYPE_NULL の公式説明は、豊富な編集接続を提供しない入力先で制限されたキー生成が必要になり得るというものです。IME 全般の使用不能を意味しません。本製品が物理キーを渡して直接入力に限定する方針と、Android 全体の制約を区別します。[TYPE_NULL の公式仕様](https://developer.android.com/reference/android/text/InputType#TYPE_NULL)

### 指摘 5: 半角カナの期限

K02 はフェーズ 2、互換性文書の共通操作末尾はフェーズ 4 まで、U10／D04 は該当実装前となっています。「フェーズ 4 まで」は早期決定を禁止していませんが、フェーズ 2 の受入前に決める必要性が文書間で一貫しません。標準キーの確定とフェーズ 4 のカスタマイズを分ける修正は妥当です。新しい実装タスクを増やす指摘ではなく、既存期限の統一です。

### 指摘 6: 進捗と環境情報

「すべて Android 側は未実装」と D01 の未取得扱いは、限定エンジン・基盤の実装と実機報告がある現在の記録と一致しません。進捗参照を `phase1.md` に集約する修正は妥当です。限定エンジンで動く例があることから K01〜K19 の達成を宣言することも避けます。

一次レビューの修正案にある「正確な API」を未取得の例に含める部分は訂正が必要です。`phase1.md` の「ADB 接続と性能測定の予備確認」には API 36 とビルド番号 `BP2A.250605.031.A3` が既にあります。未記録のアプリ版、特定の手動試験時の選択レイアウト、統制された性能測定・合格値と区別します。フェーズ 0 完了時の記録を残す場合は当時の記録と明示すればよく、フェーズ 1 を完了にする必要はありません。

## Android の実現範囲に関する独立確認

S02／N03／N08、I05／I06 は、内部バッファと入力先編集を分離し、取得・接続の制約、外部の選択変更、古い非同期結果を扱っています。入力先編集を全アプリで同じ動作にする要求ではありません。InputConnection の取得 API には失敗・部分取得があり、同時に選択移動・削除などの操作も提供されています。この制約は条件付き編集を必要とする根拠であり、既存文字の編集全般を不可能とする根拠ではありません。[InputConnection の公式仕様](https://developer.android.com/reference/android/view/inputmethod/InputConnection)

既存のひらがなを明示選択して読みとして扱う例は A01 の説明に追加できますが、将来の条件付き再変換の具体化です。今回新しい必須機能に引き上げる必要はありません。内部 Q、入力先への限定的な編集、既存バッファ全体の Emacs 操作を混同しない一次レビューの区別は妥当です。
