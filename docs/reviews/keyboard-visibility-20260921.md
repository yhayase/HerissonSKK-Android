# キーボードの不要表示への対応

## 問題と表示条件

ホームや文字入力のない全画面でスクリーンキーボードが表示され、利用者が隠しても後の通知・描画更新で再表示される問題を扱います。[表示条件](../keyboard-visibility.md)を定義しました。

原因は、有効な入力接続を画面表示の必要条件と取り違え、描画更新のたびにIMEから表示を要求していたことです。物理入力のポップアップに必要な窓と、画面の文字キーの表示要求を共用していました。

## 修正

- 文字キーは、文字入力可能な入力属性と接続があり、OSまたは入力先が表示を要求した場合だけ表示します。パスワード欄も対象です。`TYPE_NULL`は対象外です。
- 描画、候補・辞書・カーソル更新からスクリーンキーボードの表示要求を出しません。
- 物理入力の表示は文字キーと分離します。Android 13以降は、IME自身のトークンに結び付けた透明・非フォーカス・非タッチの1pxの窓をポップアップの親にします。下部領域は予約せず、主IME窓を置き換えず、追加のオーバーレイ権限も要求しません。それより前の経路はAndroidの候補専用ウィンドウと高さゼロのViewを使います。
- 非表示後の受動更新と同一入力欄の接続再開始では、物理用の窓も再表示しません。新しい入力先か実際の物理キー操作で再開できます。
- 回転時はAndroidが保持する表示要求を使い、候補専用ウィンドウの再生成を扱います。独自の表示許可状態を重複して持ちません。

## 独立レビューと指摘の再検証

表示設計・実装と端末試験を別担当がレビューし、指摘は実装担当またはさらに別の担当が検証しました。

- タッチ側を隠した後も、物理側へ切り替えると窓が開く経路を修正しました。
- 同じ入力欄の`restartInput`が非表示状態を解除する経路を修正しました。
- 単なるViewでは`AT_MOST`測定時に高さが640になりました。両APIの単体試験が検出し、独立レビューも製品側の問題と確認したため、実測高さをゼロにするViewへ変更しました。
- 非表示試験を「一瞬消えていれば成功」にせず、一定時間の非表示継続を検査しました。全画面試験も、実際にOSが`TYPE_NULL`の入力接続を確立したことを確認します。
- 通知領域を閉じるために送ったBackが背後の試験Activityへ届き、通知領域が残る試験側の問題を検出しました。独立した調査・再検証に基づき、通知領域が開いたことを確認してからシステムのcollapse操作で閉じ、終了時にも復旧する手順へ修正しました。
- Android 15の候補専用ウィンドウでは、表示要求トークンがない呼び出しが以前の窓と関連付けられ、候補が取り付けられても表示されない問題をフル試験で検出しました。単独の2件では成功したため、全19件の順序で再現し、別担当もAOSPの経路を確認しました。文字キーを開く自己要求へ戻さず、IMEトークンを使う非タッチの親窓で分離します。
- 物理表示を閉じた後の2回目のBackが再表示を許可する経路も修正し、入力先から離れる操作として扱います。
- 適用範囲をAndroid 13以降としました。Android 11・12にも同じ問題があるというレビュー指摘は、別担当による呼び出し箇所の照合で撤回しました。Android 13で候補窓の表示にもトークン経路が加わり、同時に非タッチIME窓を主IME窓から除く扱いが利用できるため、この境界で経路を分けます。[Android 13のInputMethodService](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-13.0.0_r1/core/java/android/inputmethodservice/InputMethodService.java)と[WindowManagerService](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-13.0.0_r1/services/core/java/com/android/server/wm/WindowManagerService.java)を参照しました。
- タッチ操作試験9件は、入力欄へフォーカスを移すだけで文字キーの表示を期待していました。独立レビューで、旧実装の自己表示に依存した試験側の問題と確認し、入力先アプリの通常の`showSoftInput`要求を明示する手順へ修正しました。共有Activityには自動表示を加えず、非表示・物理入力の試験条件を維持します。
- Android 8の候補窓は画像とWindowManager上では正しく移動していましたが、アクセシビリティの座標が初回表示位置のままで、7候補中ほとんどが不可視と判定されました。試験のキャッシュ除去と`refresh()`後も誤った座標が返ることを別担当と確認しました。単独試験の成功や画像だけで問題なしとはせず、可視性の検査を維持し、再現を確認したAndroid 8.0（API 26）だけ、窓の位置変更時に同じViewを取り付け直します。候補本文・選択状態・入力フォーカスは保持し、位置が同じ更新では通常のレイアウト更新を続けます。API 27以降でも同じ問題が起きるとは断定していません。
- 構成変更用の独自表示許可フラグを追加する案は採用しませんでした。AOSPの構成再生成は保持済み表示要求だけを再生し、通常の非表示操作でその状態を解除するためです。

## 検証

修正前APKのSHA-256は`b7da0fe90c58cd2053650f7a45d6288c8a8ba7a23bc05279e0751d7dc6a1a8d6`です。追加した端末試験をAndroid 15で実行し、非表示後の再表示と全画面での不要表示の2件が失敗し、通常入力欄への再表示・パスワード入力の対照1件は成功しました。

ローカル検証`20260921T030024722391Z`は成功しました。コア310件、Android単体850件、ホスト26件、debug/releaseのlint、APK・ライセンス・manifest検査が成功し、失敗・エラー・スキップはありません。途中の限定単体試験ではRobolectricのネイティブ初期化エラーが発生しましたが、新しいプロセスで同じ試験を再実行して成功し、続く全検証も成功しました。

修正版APKのSHA-256は`5d3dc4369d55d26eef3fa5b7779aacbb7a7bc878bcbeb2d10c7fba28cf1471d3`です。Android 8.0（API 26）・Android 15（API 35）で各43件、計86実行が成功しました。各端末の内訳は表示条件3件、物理入力・Unicode 19件、ポップアップのライフサイクル4件、候補表示4件、狭幅・文字倍率2の表示4件、タッチ操作9件です。Android 8の4番目の候補選択は、修正前に繰り返し失敗した同じ可視性検査を維持して成功しました。設定を変更する試験では復元も成功しています。

配布APKと全試験の対応は`build/distributions/keyboard-visibility-20260921-5d3dc436/manifest.json`へ保存し、全端末試験のAPKハッシュ一致を確認しました。実行ログは`build/reports/keyboard-visibility-20260921/`にあります。

Xiaomi Pad 8・Pixel 7での今回の修正版の実機確認は未実施です。API 33・34の分岐はAndroidソースで確認しましたが、端末実行はAPI 26・35です。本番署名・公開・端末への転送は行っていません。
