# Android IME 要件の独立レビュー（2026-09-16）

履歴資料です。対象時点の判定を保持しています。現在の仕様・残件との区別は [レビュー履歴の案内](README.md) を参照します。

## 対象と結論

対象は `docs/requirements.md`、`docs/compatibility.md`、`docs/roadmap.md`、`docs/validation-plan.md` です。実装済み機能の合否ではなく、実現範囲、仕様の明確さ、DDSKK 参照との一致を確認しました。レビュー時の DDSKK は 17.2、タグ `ddskk-17.2_Mena`、コミット `e8bf68b27021c29781dbfa6a8ef7b770565bdb5b` です。

Android IME では実現不能な処理を、現文書が無条件の必須要件として要求しているとは確認できませんでした。内部編集と入力先編集の分離、取得できない範囲を推測して削除しない条件は適切です。ただし、内部の `Q`／`q` 操作、Enter の参照説明、送り条件の参照設定には修正すべき不足があります。特殊な入力欄の例外規則と、文書間の期限・進捗情報にも整理が必要です。

重大度は P1＝実装前に直すべき重大な誤仕様、P2＝互換性・受入判定に影響する仕様不足または不整合、P3＝進捗・記述の整合性の問題とします。今回、P1 に相当する指摘はありません。

## Android IME と Emacs バッファの境界

| 操作 | 評価 | 現文書との関係 |
| --- | --- | --- |
| IME が保持する `▽にほん` の途中編集・変換 | 内部状態で実現できます。入力先の全文取得は必要ありません | F05、S02、N01 の分離は適切です |
| IME の登録用バッファの編集・再帰登録 | 内部状態で実現できます。子から親への反映と最上位での確定を分けられます | F06、K10、登録状態遷移の条件は適切です |
| 既存のひらがなを明示選択し、取得した文字を読みとして再変換 | 入力先が対象文字・範囲と編集操作を提供する場合は検討できます。ひらがなだけなら、その文字列を読みとして使う経路に漢字からの読み推定は不要です | A01 の条件付き再変換に収められます。全アプリ対応は保証できません |
| `Q` で印を付け、Emacs のカーソル移動で任意の既存バッファを変換対象へ取り込む | Emacs と同じ無制限の範囲操作は保証できません。ただし `Q` というキー自体が IME で使えないわけではありません | X01 の除外と、ロードマップの内部 `Q` の区別は妥当です。具体的な内部操作が不足しています（指摘 1） |
| 未確定のない入力先での C-b/f/h/d/k、行・単語移動 | 取得範囲と入力先の操作対応に依存します。論理行と表示行の移動も区別が必要です | S02 は条件と未決事項を既に明記しています。Emacs 全般が不可能という理由で F13 を削除する根拠はありません |

Android の `getSelectedText`、`setComposingRegion` は、既存の選択文字や範囲を使う処理のための API です。一方、取得 API は失敗・部分取得があり、キー送信も受信時のフォーカスを保証しません。これらは「既存文字を一切編集できない」という根拠ではなく、範囲・接続の確認と失敗時の扱いが必要な根拠です。[InputConnection の公式仕様](https://developer.android.com/reference/android/view/inputmethod/InputConnection)

## 指摘

### 1. P2: 内部の Q と、見出し語に対する q の受入操作が抜けています

- 対象: `docs/compatibility.md:22-24,47,59-70`、`docs/requirements.md:24-25`、`docs/roadmap.md:25`。
- 根拠: 固定 DDSKK の `skk-vars.el:947-949` は `q` を `skk-toggle-characters`、`Q` を `skk-set-henkan-point-subr` に割り当てます。`skk.el:3298-3318` の Q 処理は現在位置から新しい見出し語入力を開始でき、既存文字の取り込みだけの機能ではありません。`skk.el:935-972` は見出し語に対する文字種変更・確定も行います。リリースの `test/skk-test.el:205-216` には `Q k a n a q RET` などの受入例があります。
- 不足: K02 は通常状態での `q kana` しか例示せず、Q は X01 の除外例に登場します。ロードマップは内部 Q を別途定義すると記載していますが、機能一覧・状態別キー表・未決期限に対応する操作がありません。
- 影響: `Q` を既存バッファ機能として丸ごと除外する実装や、`▽かな` での `q` を通常モード切替として処理する実装が、現在の明示的な受入例を通過できます。これらは入力先の既存文字を操作せず実現できる基本操作です。
- 修正案: 通常状態から空の見出し語を開始する Q、見出し語の q による文字種変更、候補中の Q／q を状態別に定義します。`Q kana SPC`、`Kana q` などの具体例をフェーズ 2 の受入条件に追加し、内部カーソルが途中にある場合の対象範囲は U01 と結び付けます。既存バッファの Q と条件付き再変換の区別は維持します。
- 不確実性: 内部 Q を今後採用しないという製品判断も可能ですが、その場合は DDSKK との相違として明記する必要があります。既存文字取り込みの除外自体は誤りと判定していません。

### 2. P2: Enter の説明が DDSKK と同等である範囲を越え、残余ローマ字の期待値も一意ではありません

- 対象: `docs/compatibility.md:11,65`。
- 根拠: 固定 DDSKK の `skk.el:5214-5241` は、`skk-egg-like-newline` に加えて `skk-henkan-mode` がある場合に改行を抑止します。通常のかな状態で未消化ローマ字だけがある場合まで同じ条件ではありません。後述の独立実行では、この設定を t にしても `n RET` は `ん` と改行、`k RET` は改行だけでした。
- 不足: 11 行目は「未確定入力があれば確定だけ」という Android 方針全体を当該設定に相当すると説明します。65 行目の `n` 以外の「規則上の確定結果または残余文字」は、例えば標準設定の `k Enter` が `k` を残すか消すかを判定できません。
- 影響: DDSKK をそのまま期待値生成器にすると Android の送信・改行抑止方針と衝突します。また、同じ標準入力列で異なる出力を合格扱いにできます。
- 修正案: 見出し語・候補の Enter と、通常状態の未消化ローマ字の Enter を分け、後者は Android 独自の改行・送信抑止であると明記します。`n`、`k`、複数文字の未消化列について Enter／C-j 後の文字列とモードを固定します。カスタム規則の場合の終端処理も、標準ケースと分けて定義します。
- 不確実性: 改行を抑止する製品方針を誤りとは判定していません。修正対象は参照説明と未確定の出力規則です。

### 3. P2: 送り条件の一致候補を優先する K04 に対応する参照設定が不足しています

- 対象: `docs/compatibility.md:9-14,25,43,51`。
- 根拠: 固定 DDSKK の `skk-vars.el:1628-1643` では `skk-henkan-strict-okuri-precedence` の標準値は nil です。t の説明は、個人辞書 `おおk /大/多/[く/多/]/[き/大/]/` に対して `おおく` の一致候補 `多く` を先にし、その後 `大く` を出すというものです。これは `skk-henkan-okuri-strictly` による不一致候補の除外とは別です。
- 不足: K04 は一致候補の優先を採用済みとしていますが、「基準と設定」には対応する DDSKK 設定がありません。R01 の厳密照合の未決状態と、既に採用した優先順位の区別も読み取りにくくなっています。最小辞書 `かk /書/` だけでは、優先順位の違いを検出できません。
- 影響: 標準設定の DDSKK と採用仕様から異なる期待候補順が得られます。一致・不一致候補を両方含む試験を追加した時点で、互換性違反か設定差か判定できません。
- 修正案: 一致優先を Android の採用設定として明記し、比較用 DDSKK では `skk-henkan-strict-okuri-precedence = t` とすることを記録します。優先と除外を分け、双方の候補と送りブロックを含む具体的な個人辞書・期待順を固定します。複数辞書全体への適用範囲は U06 と併せて決めます。
- 不確実性: K04 の一致優先そのものは合理的な採用仕様です。DDSKK の標準値へ戻す必要があるという指摘ではありません。

### 4. P2: パスワード欄の開始モードと、通常のモード切替キーの優先関係が未定義です

- 対象: `docs/requirements.md:24,33,55,161`、`docs/compatibility.md:13,63`、`docs/validation-plan.md:45`。
- 根拠: パスワード欄は直接入力で「開始」するとされる一方、通常の ASCII 状態の C-j はひらがなへ切り替える規則です。I10 はパスワードを候補表示へ露出しないことを要求します。参考として `docs/phase1.md:10` の現行基盤は、パスワード欄と `TYPE_NULL` を直接入力として扱い、候補を出さないと記録しています。
- 不足: 特殊な入力欄で通常のモード切替を無効化するのか、かな入力を許し表示を抑止するのか、例外規則がありません。`TYPE_NULL` の扱いも、対象 4 文書の機能・状態表には位置付けられていません。
- 影響: フェーズ 2 で通常の C-j 規則を実装した際に、基盤が持つ制限を落としても通常の開始モード試験は通過します。現状の記載だけでは、パスワード欄で C-j の後に変換を開始した場合の期待結果を定められません。
- 修正案: 通常キー表より先に評価する入力欄の例外を記載します。パスワード欄での C-j・大文字・SPC・登録操作の扱いと候補非表示を受入ケースにし、`TYPE_NULL` の直接入力制限も明記します。
- 不確実性: パスワードの露出が現実装で発生することを確認した指摘ではありません。実装は既に保護している可能性が高く、要件と試験による保護の明文化を求めるものです。学習禁止欄一般に、候補表示まで禁止するという意味ではありません。

### 5. P2: 半角カナの標準キーを決める期限が、必須実装時期と一致しません

- 対象: `docs/compatibility.md:23,70`、`docs/validation-plan.md:73`、`docs/requirements.md:187`。
- 根拠: K02 の半角カナはフェーズ 2 の必須ですが、互換性仕様の 70 行目は半角カナ切替の詳細を「フェーズ 4 まで」に決めるとします。requirements の U10 は該当機能実装前、validation-plan の D04 も該当実装前とします。
- 影響: フェーズ 2 の完了時点で半角カナへの物理キー操作が未定義でもよいと読む余地があり、物理キーだけで完結する受入条件と整合しません。
- 修正案: 標準の切替キーはフェーズ 2 実装前に固定し、そのカスタマイズはフェーズ 4 と分けます。削除確認・補完の期限もそれぞれの実装フェーズにそろえます。
- 不確実性: requirements の U10 を優先すれば期限は既に適切です。作業の追加ではなく、相反する期限表記の解消です。

### 6. P3: 実装・実機試験の進捗と環境の未決表示が古いまま残っています

- 対象: `docs/compatibility.md:18`、`docs/validation-plan.md:7,70,79`、`docs/roadmap.md:47`。
- 根拠: compatibility は「すべて Android 側は未実装」、validation-plan は「実装・実機試験は次のフェーズ」とし、OS 版・キーボード型番・接続方法を未取得扱いにしています。一方、requirements の `172` 行目には Android 16、HyperOS 3.0.303.0、任天堂 Bluetooth キーボードの確認が記載され、roadmap の `47` 行目も基盤実装と初回手動確認の完了を記録しています。
- 影響: 完了した環境確認を重複実施したり、基盤の実装済み範囲と未実装の本格コアを取り違えたりします。
- 修正案: 互換性一覧は「完成した互換コアとしての達成は未判定」などに更新し、実装状況は phase1 を参照します。環境の既知情報を反映し、正確な API・アプリ版・測定値など、まだ取得していない項目だけを未決として残します。
- 不確実性: 初回確認はユーザーの手動報告であり、全アプリ・全入力欄の実機合格を意味しません。その限定は維持すべきです。

## 既にある適切な条件と、誤検知にしない事項

- `requirements.md:85` と `roadmap.md:187` は、内部編集と入力先編集を分け、範囲を確認できない場合に推測で削除しないことを明記しています。S02 の行・単語境界、Meta、失敗時のキー処理は未決として U02 で期限を持っています。詳細未確定だけを理由に「Android で不可能」とは判定しません。
- A01 は取得可能な選択文字列と確定履歴を使う条件付き機能です。元の読みの復元を保証しません。既存のひらがなを明示選択して読みとする例を追加すれば、ユーザーが期待する操作を説明しやすくなりますが、現時点で無条件対応を約束しているわけではありません。
- I05／I06、N03／N04 は古い非同期結果、外部カーソル変更、別入力欄への誤挿入を扱います。内部の途中編集を禁止する必要はありません。
- 登録文字を入力先へ流さない規則、子の登録を親だけへ反映する規則、保存済みの子辞書項目が親取消後も残る規則は明確です。
- K15 の未受諾補完を SPC の検索に含めない条件は、固定 DDSKK の `skk-dcomp.el:583-585` にある変換前の補完クリーンアップと矛盾しません。
- 数値変換 `#0`〜`#5`、`#8`、`#9` は固定 DDSKK の `skk-vars.el:4657-4665` に対応します。`#6`／`#7` が必須一覧にないことは脱落ではありません。
- 不正辞書・非対応表現を黙って成功扱いしない条件、U06 による辞書統合の確定期限、任意 Lisp を対象外とする境界は既にあります。任意 Lisp の非対応から、辞書の静的なエスケープ表現まで一律非対応にすべきとは判断しません。具体的な対応表現は辞書実装前の定義事項です。
- 回転・切断後の継続は将来改善として分類され、現状許容と区別されています。Android が変換確定を強制するという誤った前提は置いていません。

## 確認方法と限界

4 文書を読み、必要に応じて `docs/phase1.md` の現行基盤記録と照合しました。DDSKK は上記固定コミットのソースとリリース同梱テストを確認しました。ISO-2022-JP のソースは文字コード変換して読みました。ファイル全体の一部に変換不能文字がありましたが、報告で根拠とした行の日本語とコードは読み取りできています。

以下は一時辞書を使用する DDSKK の `skk-e2e-test` による独立プローブです。ユーザー設定を読み込まず、記録保存を抑止しました。

```sh
emacs --batch --quick \
  --directory /home/hayase/tmp/ddskk \
  --directory /home/hayase/tmp/ddskk/test \
  --load /home/hayase/tmp/ddskk/test/skk-test.el \
  --eval '(require (quote ccc))' \
  --eval '(setq skk-init-file "/tmp/skk-review-no-init" skk-record-file "/tmp/skk-review-record" skk-keep-record nil skk-save-jisyo-instantly nil)' \
  --eval '(let ((skk-egg-like-newline t)) (princ (format "Q-empty=%S\nn-RET=%S\nk-RET=%S\n" (skk-e2e-test nil nil (function skk-mode) "Q k a n a C-j") (skk-e2e-test nil nil (function skk-mode) "n RET") (skk-e2e-test nil nil (function skk-mode) "k RET"))))'
```

終了コード 0。出力の意味は次のとおりです。

```text
Q-empty: "かな"
n-RET: "ん\n"
k-RET: "\n"
```

最初のプローブでは `ccc` 未ロードによる pre-command-hook 警告が出たため、`require` を追加した上記コマンドで再確認し、警告なしで同じ結果を得ました。

Android の公式 InputConnection 仕様も確認しました。Android 実装のコードレビュー、アプリ別の実機試験、DDSKK テスト全体の再実行、自動差分検証は実施していません。したがって、仕様の不足を現在の実装不具合と同一視していません。
