# 入力欄との編集互換性と登録取消の追加修正

履歴資料です。対象時点の判定を保持しています。現在の仕様・残件との区別は [レビュー履歴の案内](README.md) を参照します。

## 報告と受入条件

実機で、最終行への C-p/n、末尾文字の C-h/d、Firefox のアドレス欄と X の入力欄で編集が動かない問題が報告されました。Keep では編集途中から停止し、C-m がきっかけの可能性がありました。M-</> で範囲が選択され、候補ゼロ件の登録から C-g で戻ると読みも失われる問題も対象です。

次を受入条件とします。

- 最終行・末尾文字でも移動と前後削除ができ、改行後も同じ入力欄で編集を続けられます。
- 取得 API が一部未対応、または絶対位置不明の入力欄でも、入力先が提供する標準操作を利用できます。
- C-m は改行文字を入力し、送信・検索の editor action に変換しません。
- M-</> は範囲選択を作らず移動します。
- 候補ゼロ件から自動で始まった登録の C-g は、読みを編集できる状態へ戻します。候補を使い切った登録では最後の候補表示へ戻ります。

## 原因と採用した変更

編集ポートが取得窓の端を含む計画を拒否していたため、末尾の左右移動だけを直した前回版では、上下移動と削除に同じ制限が残っていました。境界を証明できない対応操作は、入力先の標準キーで一度だけ実行します。Unicode 分節と表示行の扱いは入力先に依存し、内部編集の ICU 規則との一致を約束しません。取得窓末尾を文書末尾と推測して削除長を計算する実装は採用していません。

`getSurroundingText` の null を取得不能として抽出 API に切り替え、`offset == -1` は公式仕様の「絶対位置不明」として扱います。相対応答しか得られない場合は二回の同じ方式の応答を照合し、絶対位置を作らず入力先の操作に委ねます。不正範囲、過大な応答、差分抽出などは拒否します。本文を取得できない場合も C-m は一度だけ `commitText("\n", 1)`、選択ありの切り取り・コピーは入力先のコンテキスト操作を使います。

事後確認の不一致や API の拒否がポート全体を使えなくしていたため、その要求を終了し、同じ版が維持されている場合は後続の別の明示的な要求を新しく取得・照合するようにしました。同じ変更の再送はしません。応答停止・例外のポート停止、保護入力の迂回、世代照合、キュー上限は維持します。

API 35 の実試験で、末尾の連続 C-h の二打目が、遅延した選択通知のため失われることを検出しました。標準キーによる削除も移動と同じ直列の操作列に残し、通知前の古い選択位置から次の削除を計画しません。試験へ待ち時間を追加して回避していません。さらに改行を入力先が変換した際の事後不一致で、既に待機していた C-b が捨てられる事象を確認しました。同じ版の後続コマンドは新しく取得して処理し、元の改行要求の再送とは区別します。絶対位置の通知が本文取得より遅い場合も、妥当な二回の取得を照合して標準操作へ委ねます。

M-</> の文字入力に必要な Shift のラッチは、標準移動キーを送る前に `clearMetaKeyStates` で解除します。通知から自分の範囲選択だと推測して後から解除する方式は、利用者の選択を壊す可能性があるため採用しません。

登録には、候補ゼロ件の検索から入ったことを保持し、取消時に保存していた読み状態を復元します。明示的な登録、保存待ちの取消、候補を使い切った登録の既存の意味は維持します。

## 独立レビュー

編集ポートの非同期・境界処理は Astra / low、登録取消は Terra / medium、キー配送と WebView 試験は Sol / medium が担当し、Sol / medium が独立レビューしました。非同期通知の修正後も API 35 の WebView と API 26 の改行変換試験で再発したため、同じ境界の調査を Astra / high へ一段階引き上げました。以下の指摘を反映しました。

- null と不正な非 null 応答を区別し、不正な情報から標準削除へ進めません。
- 本文取得不能時に Enter を送る案を取りやめ、C-m が投稿・検索へ変わらないようにしました。
- 選択のないコピー・切り取りは、取得不能経路でもコンテキスト操作を呼びません。
- 遅延選択通知から操作の帰属を推測する選択解除は取りやめました。
- 相対位置しか分からない場合の絶対選択照合の限界を設計書へ明記しました。

取得不能時の改行も標準操作の列を維持し、改行通知で次の移動要求が捨てられる問題を修正しました。WebView の試験では、同じ View 内で HTML の入力欄を替えた際に `isActive` だけでは新しい接続の準備を確認できない点を独立レビューで検出しました。DOM のクリック完了を確認してから初期位置を設定し、接続の再作成を明示的に待ちます。新しい接続の初期位置がまだ古い場合だけ、準備段階の接続更新を最大8回行います。操作対象のキーは再送せず、時間待ちで成功を推測しません。

既存の E2E は選択の開始だけを見ていたため、開始・終了の両方を検査するようにしました。Shift/Alt 自体の押下も注入し、単にイベントの meta 値だけを指定する試験から拡張しました。

## 検証と制約

検証結果と配布 APK は [作業記録](../work-status.md) と [配布台帳](../distribution.md) に記録します。試験には、通常 EditText、取得なし・抽出のみ・絶対位置不明・改行を変換する接続、ローカル HTML の WebView textarea/contenteditable を使います。試験用 WebView にネットワーク権限は追加しません。

Firefox、X、Keep の実アプリと Xiaomi Pad 8 の物理キーボードはこの環境で確認していません。WebView の合格をこれらのアプリの合格とは扱いません。標準キー配送は非同期で、送信後のフォーカス変更や入力先独自の Unicode 処理には依存します。相対応答が安定していても、それが入力先内部で既に古い場合の絶対選択不一致は検出できません。C-k や単語移動など、取得範囲から計画できず標準経路もない操作には制限が残ります。入力先が改行文字を拒否・変換する場合、C-m が必ず改行として表示されるとは保証しません。
