# 入力UIの実機指摘への対応

2026年9月21日の実機確認で挙がった問題を扱います。先行する自動試験の成功とは区別し、今回の症状に対応する回帰試験と独立レビューで確認します。以下は修正と検証の記録です。独立レビューと自動回帰検証を完了しました。

## DDSKKの参照確認

ローカルのDDSKK 17.1（Neppu）をEmacsのバッチモードで起動し、実際のキー入力を実行しました。検索結果だけを固定する関数に置き換え、入力・変換・確定の処理はDDSKKのものを使っています。

| 入力 | 変換表示 | 辞書検索キー | Ctrl+j後 |
| --- | --- | --- | --- |
| `qKaKu` | `▼書ク` | `かk`、送り条件`く` | `書ク` |
| `Nihon.` | `▼日本。` | `にほん` | `日本。` |
| `Nihon]` | `▼日本」` | `にほん` | `日本」` |
| `Nihon:` | `▼日本：` | `にほん` | `日本：` |
| `Nihon;` | `▼日本；` | `にほん` | `日本；` |

カタカナの送りは表示・確定時の文字種であり、辞書キーと送り条件はひらがなです。区切り記号は検索キーに含めず、変換部分の後ろに残ります。[DDSKKの公式説明](https://github.com/skk-dev/ddskk/blob/master/docs/06_apps.rst)にも区切り文字による自動変換と既定の対象文字が記載されています。

実行スクリプトと出力は`build/reports/acceptance-fixes-20260921/ddskk-reference.el`、`ddskk-reference.txt`に保存しています。

## 調査で確認した原因

- 物理入力のインライン段階ではコアの候補メニューが空ですが、表示側が画面キーボード用候補に置き換えていました。そのため、選択キーを受け付けない段階に選択ラベルが表示されていました。
- 物理候補の収容件数が最大2行に制限され、実際のポップアップの幅・高さと一致していませんでした。
- 未完ローマ字と送りあり候補の予測は、通常のかな前方一致だけでは扱えません。入力途中のかなの可能性、辞書が持つ送り条件、確定時の学習先を分けて検討します。

## 対応と検証

| 対象 | 修正後の動作 |
| --- | --- |
| カタカナの送り・区切り記号 | 辞書のキーと表示する文字種を分け、送りは入力モードに合わせます。区切り記号は変換候補の後ろへ一度だけ付け、学習する語には含めません |
| 物理候補の選択・ページ送り | インライン段階では候補一覧を出さず、その候補をメニューから除きます。測定したページ境界を表示・選択キー・前後移動で共用します |
| 物理候補の読みやすさ | 本文を折り返し、注釈は右側の一行表示とします。固定したラベル幅と行の区切りを使い、注釈の有無で本文の開始位置を動かしません |
| 画面側のページ操作 | 無効になった左右の三角形自体を薄い灰色にします |
| 未完ローマ字の予測 | 使用中のローマ字規則で到達できる出力を検索し、標準規則の`n`ではな行・`ん`を含めて一つの順位へ統合します。検索途中・上限超過は候補なしと区別します |
| 送りありの予測 | 送り入力前の予測で、辞書に明記された送り条件や学習した送りを使い、送り込みで表示・確定します。送り条件を持たない外部辞書の語幹だけから活用形は生成しません |
| フリック | 単純な大文字化以外の割当をキー上へ常時表示します。長押しは約200ミリ秒、上下移動時は即座にガイドを表示し、中央・上・下の有効な入力を強調します。Shift、複数の指、取消、画面端も検査します |

## 独立レビューでの追加指摘

| 指摘 | 再検証・対応状況 |
| --- | --- |
| 別のキーを離すと、まだ押しているキーのフリックガイドが閉じる | 別担当が共有ポップアップと各キーの取消経路から再確認しました。表示の所有キーを照合し、古い遅延表示と取消を無効化します |
| 一回Shiftを別のキーが消費した後も、押下中キーのガイドが大文字を示す | ガイドの表示と指離し時の出力を照合しました。Shift状態の変化時に押下中のガイドも更新し、一回Shiftの消費順序は維持します |
| 未完ローマ字の予測展開が、正当な残余規則で無限再帰する | 独立レビューと別担当の再検証で確認しました。`kk → っ`、残余`k`だけを持つ規則では結果件数の上限が働きません。明示的な処理量の上限と非再帰処理が必要です |
| メモリ内辞書の予測で、処理量を数える前に全見出し語を収集している | 別担当が、見出し語の列挙・保持・ソートが上限判定より先に実行されることを確認しました。重複した見出し語の走査も処理量へ含めます |
| `Ka`から`書く`を選ぶ試験は送りありを試していない | 別担当の再検証により不採用としました。この試験は辞書の`[く/書/]`という明示条件を予測へ含める確認です。`KaKu`へ変更すると通常の送りあり変換になり、予測の回帰確認を失います。試験名と説明を明確にしました |
| Page Downが最初の候補メニューを飛ばす／従来の固定件数が変換途中に変わる | 全コア試験の既存2件が検出し、別担当が実装の回帰と確認しました。インラインから最初のメニューへの境界と、変換開始時に固定した従来の件数を維持します。既存の期待値は変更しません |
| 長音用のキーが直接英数でも`ー`を入力する | 実IME試験で検出し、独立QAが確認しました。キーが送る値をASCIIの`-`へ戻し、かなモードでの長音化はコアへ任せます |
| ガイドの文字をアクセシビリティで取得できない／ガイドがキーの下へずれる | 録画からガイド自体の表示を確認しました。操作を受け付けない窓なのでアクセシビリティ一覧を検査条件にしません。一方、画面座標をIME子窓の座標として渡す位置ずれは実不具合と別担当も確認したため、キー基準の配置へ修正します。端末試験では実際の位置と中央・上下の強調色を画像の画素で検査します |
| Android 8でフリックガイドの一部が欠ける | ウィンドウの実測で132pxの高さが93pxへ切られることを確認し、別担当が親IME窓によるクリッピングと再確認しました。キー相対の位置を維持してクリッピングを解除し、両APIで画面端も検査します |
| Android 14以降の拡大文字で候補件数の測定が表示と一致しない | 別担当が公式の非線形SP変換仕様と表示側のTextViewを照合しました。横幅のSP変換と、行高を測るTextViewを表示側へ合わせ、実描画の最大収容行数と比較します。単独StaticLayoutでは代替フォントの行間既定値も異なるため、文字倍率だけの修正では不十分でした |
| 候補メニューから登録を取り消す端末試験で、復元先が読みになっている | 別担当の調査とさらに別担当の再検証により試験の競合と判定しました。登録窓のアクセシビリティ公開より先に読みが入力欄へ反映され、試験が直前候補を上書きしていました。候補だけを保存し、登録窓を待ってから取消とラベル選択を検査します |
