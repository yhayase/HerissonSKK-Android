# 自律開発の進め方と品質判定

作成日: 2026-09-16

## 目的と権限

物理キーボードで日常利用できる Android SKK IME を、既存の要件とロードマップに沿って開発します。ユーザーの「人間の関与が本質的に必要な部分以外は Codex が進める」という指示に基づき、調査、設計、作業分割、実装、検証、修正、記録は Codex が担当します。通常の技術選定や各作業の開始について、繰り返し承認を求めません。

本書は開発手順です。製品要件の正本は requirements.md、操作の正本は compatibility.md、時期は roadmap.md とします。提案を実装する際は採用理由と対応する受入例を記録し、製品文書を同時に更新します。過去のレビュー指摘より、修正後の仕様とレビュー反映記録を優先します。

品質は無欠陥の約束ではなく、要求に対する検証結果、失敗時の保護、既知の制約を再現可能な形で示すことで判定します。

## 人間が必要な境界

| 項目 | Codex が進める範囲 | 人間が必要な場面 |
| --- | --- | --- |
| 設計・実装 | モジュール分割、アルゴリズム、保存方式、テスト、修正、局所的なリファクタリングを判断します | 通常は不要です |
| 未決仕様 | 固定 DDSKK、既存要件、安全性、変更しやすさを比較し、整合する技術的詳細を決めます | 要件が相反し、用途や好みなしには選べない場合だけ、具体例と推奨案を提示します |
| 操作設定 | 既存の確定値を守り、可逆な未決初期値は理由を記録して選びます | 操作感の最終評価や、既存の必須機能を削る判断が必要な場合です |
| 実機試験 | 接続済みの試験環境で可能な自動化、合成入力、ログ解析、APK の準備を行います | 端末の接続・解除、OS が要求する本人操作、実際の Bluetooth 打鍵、主観的な使い心地の確認です |
| データ・外部への影響 | 一時辞書、検証用アプリ、復旧可能な試験データで検証します | 個人辞書の不可逆な消去、外部への公開・送信、費用やアカウント上の同意など、新たな本人判断が必要な場合です |

質問が必要でも、影響する作業だけを保留し、独立した作業を続けます。人間へ渡すときは、操作手順・期待結果・判断に必要な成果物を先に準備します。一般公開は日常利用版の開発とは別の到達点です。

## 作業単位と完了条件

作業は「一つの利用者の操作を、入力から出力まで検証できる」程度に分割します。各作業に対象の F／N／K／I／U ID、採用仕様、変更範囲、受入例、検証方法、未実施項目を持たせます。

1. 要件・受入例から期待結果を定めます。参照実装の現在の出力や、自分の実装結果をそのまま期待値にしません。
2. 振る舞いを変える作業では、正常系に加えて取消・境界・失敗の意味のあるテストを用意します。不具合は再現テストから修正します。
3. 最小の実装を行い、関連テスト、必要な結合試験、Lint、ビルドを実行します。
4. 差分を要件に照らしてレビューします。特にテストが実装と同じ誤解を共有していないか、失敗を成功に見せていないかを確認します。
5. 指摘は根拠・再現条件を確認して修正します。無関係な改善を同じ作業へ混ぜません。
6. 結果と残る制約を記録します。関連する失敗を残したまま、その作業を完了にしません。合格後の同じ検証は、新たな変更や懸念がない限り繰り返しません。

レビューの確認観点は、仕様・状態遷移、Android 接続、データ保全・プライバシー、テストの妥当性です。同じ担当が行った再確認を独立レビューとは表記しません。別担当によるレビューを使う場合も、指摘の件数やモデル名を品質の証拠にせず、実差分と再現結果で採否を決めます。

既存の未コミット変更は保全します。コミットを作る際は検証済みの作業単位とし、他の作業の変更を暗黙に含めません。

## 検証の層

| 層 | 主な証拠 | 判定しないこと |
| --- | --- | --- |
| 純粋 Kotlin コア | キー列、辞書応答、内部状態、未確定表示、確定出力、保存要求の JVM テスト | Android アプリでの配送・描画の合格 |
| 互換性 | 固定 DDSKK 17.2 と採用設定による限定差分試験、Android 独自仕様の明示 | DDSKK の全動作への無条件追従 |
| 辞書・保存 | 特殊文字・注釈・送り条件・順序の往復、失敗注入、中断・再起動、旧辞書保持 | モックで成功しただけの実永続化保証 |
| Android 接続 | Robolectric、別アプリ instrumentation、接続拒否・遅延・セッション変更 | 実 Bluetooth の配送や全アプリ互換性 |
| 実機・性能 | Xiaomi Pad 8 の対象アプリ、物理キー、測定境界とビルド識別付き結果 | エミュレーター値による実機性能の合格 |

状態遷移が増えた時点で、生成したキー列による不変条件の試験も追加します。対象は、二重確定しない、取消で辞書を変更しない、子登録を入力先へ出さない、別セッションへ出力しない、UTF-16 を破壊しない、学習禁止で保存しない、です。失敗列と乱数 seed を残して再現可能にします。

カバレッジは試験漏れを探す補助指標です。テスト件数や一律の網羅率だけでは合格にしません。重要なガードについては、条件を外したときに対応テストが失敗するかを局所的に確認します。

## 開発順序

リリース範囲と優先順位は [ロードマップ](roadmap.md) に集約します。旧フェーズ順を今後の依存関係として再利用しません。初回必須機能の具体的な作業分割・依存関係・設定UI設計は実装前に定めます。計画の採用と実装完了を区別し、実機待ちでも独立した設計・実装・自動検証は進めます。

実機はXiaomi Pad 8とPixel 7、必須アプリと代表シナリオの方針は [検証計画](validation-plan.md) に従います。全環境の総当たりE2Eを要求しません。利用者の操作感の確認と既知の重大欠陥がないことを公開判定に含めます。

## 参照資産の取り込み

DDSKK は期待動作の比較基準です。ブラウザ版からは入力例、状態遷移、辞書契約、保存失敗の試験を抽出します。Enter／C-j、送り優先、内部編集、Unicode について既知の差を維持します。AndroidSKK は比較・不具合再現の参考とし、基盤の全面変更は既定路線にしません。

ソース・テーブル・辞書の複製前に出典とライセンスを確認します。確認できない資産の取り込みだけを止め、仕様からの実装や独自の試験は進めます。

## 継続用の記録

要件を別の大きな仕様書へ複製せず、各作業の記録に要件 ID と根拠を付けます。記録には「現在の作業、完了した証拠、残件、決定理由、次の実行手順」を残します。セッション再開時は差分と記録を確認し、完了済みの調査や承認を繰り返しません。

長時間作業の計画・検証・修正と、リポジトリ内への状態記録は [OpenAI の長時間タスクの説明](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex) も参考にしています。本書の品質判定は、このプロジェクト固有の要件から定めています。
